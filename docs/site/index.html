psi-briefing

Briefings you can read without a meeting.

Text-dense 16:9 slides in a single, self-contained HTML file. A briefing is what you send to the people who could not attend, so the deck has to carry itself.

Slides for a talk you will actually deliver are a different problem, and a different tool: psi-slides turns one Markdown source into a projection, a presenter cockpit, a reading document and a handout. The line between the two is whether anyone is speaking.

You write a document; it picks the layout

The component is chosen from the shape of your text, before anything is rendered. Four blocks of equal rank are four parallel points, so they become a bordered grid; a quotation is the takeaway, so it becomes the band at the bottom.

The example deck The tutorial deck

The example is a project retrospective: figures, a generated chart, a timeline, a reveal. The tutorial teaches the format by being written in it, and shows the Markdown next to the result on every slide.

One HTML file each. No server, no fonts to install, no network. The same example with its assets linked is how you work while writing.

The build step folds the CSS, the script and the images into the file, then checks that nothing in it still points outward:

$ tools/build-deck.sh examples/example-deck.html -o /tmp/deck.html
3/3  verify       checking for anything still external

built   /tmp/deck.html
        0.02 MB linked  ->  0.13 MB self-contained
        no external references: opens with no server and no network

One check this cannot do without a browser: open the file and confirm
  performance.getEntriesByType('resource').filter(e => !e.name.startsWith('data:'))
is empty, and that no image is broken.

That last check comes out empty on this page as well. The two screenshots above and the favicon are data: URIs, so the only thing the browser fetched to show you this document is the document.

How you write one

A Markdown file and one command. The output is ordinary readable HTML, so you can hand-tune any slide afterwards.

node tools/md-to-deck.mjs deck.md -o deck.html
python3 -m http.server 8000        # then look at it

tools/build-deck.sh deck.html      # one file you can send

What you get back

The deck, and a report of which rule fired on each slide. This is the run for the example deck; the Markdown reference says what each rule needs and what the percentage measures.

Then what it fixed by itself, and what it cannot fix for you:

      78 %  2 cards -> two columns            How a commit is counted
       fix   short row (78 %) -> cols--center; balances the gap, does not fill it
  typography: 6 marks normalised
  layout: 1 correction(s) applied

  thin rows - these need content, which no tool can invent.

It rearranges content and splits slides. It will not stretch a container to close a gap: that took one deck from 74 % to 96 % fill and made it worse (§1 of the write-up).

Two ideas do the work

Container-query scaling

Every slide is a 16:9 box with container-type: size. Everything inside is measured in cqw and cqh – never px, never rem.

So the layout scales with the slide instead of being fixed to it. Every gap and every type size keeps its proportion, which is what holds a deck together on a 13-inch laptop and a 4K projector at once.

Semantic design tokens

Every colour and face is a custom property with a meaning rather than a value: --accent, --ink, --highlight.

A theme is a :root{} override and nothing else. The generated SVG charts read the same tokens as they draw, so re-skinning a deck is one file.

To re-skin a deck you edit one file. Four of its lines, from themes/bamberg.css:

  --accent:      #00457D;
  --highlight:      #FFD300;
  --paper:      #ffffff;
  --ink:        #1a1a1a;

The dark theme that ships with it, themes/midnight.css, sets those same four names to #7aa2f7, #e0af68, #16181f and #e6e8ef, and runs to 50 lines. Copy either one, change the values, and load it after briefing.css.

When not to use it

It fits content that is already document-shaped: a retrospective, project documentation, a research summary, lecture notes, a report with numbers in it. Those already arrive with sections, comparisons and numbers in an order somebody chose.

It is a poor fit for a sparse spoken talk, the kind that runs on timing and on setting up a question before answering it. A conference keynote was built this way once and resisted both treatments: dense, the slides argued with the talk; sparse, they were empty frames with one sentence on them. That argument lived in the speaking, and a deck built to be read could not hold it.

There is also no animation model beyond click-to-reveal panels, and no speaker view. For either, use psi-slides.

iA Presenter, in particular

iA Presenter made this idea mainstream and does the same kind of thing: it analyses a slide’s content and picks a layout. The difference is the default. There, the document is a script – an ordinary paragraph is what you say, and you indent one to promote it onto the slide, so what the audience sees is the exception you opt into. Here there is no speaker, so there is nothing to demote: everything is on a slide, and the engine asks what shape the content has rather than which fragment to promote.

Which makes iA Presenter the closer relative of psi-slides, not of this. If you are going to stand up and talk, it is a mature, well-designed product and this is not a serious competitor to it.
